# HTTP discovery and individual address audit (1.9.0)

Scope: separate address actions, local HTTP detection, native-page lifecycle, and release regression coverage. Existing public listener/firewall and static-file boundaries remain covered by the [1.8.0 audit](AUDIT-1.8.0.md).

- Address buttons capture exactly their own URL; every URL has wrapping text and named Copy/Open controls. Stopping removes managed address rows; restart rebuilds them for the active port, and refreshing detection also refreshes interface addresses. Discovery addresses remain usable independently of the managed service.
- Discovery enumerates local listening TCP endpoints through Windows owner-PID tables for IPv4 and IPv6, with retries for table growth and bounded native buffer traversal. Wildcard listeners use loopback; specific bindings use their local IP, preserving IPv6 scope IDs. Process handles are disposed and unavailable process names do not fail the scan.
- Only a parsed HTTP response confirms a server, regardless of status. Non-HTTP and silent sockets are omitted. Duplicate probe URLs collapse; multiple distinct endpoints for one server are explicitly described as addresses. This cannot establish whether another application's server is temporary.
- HEAD probes disable proxies, redirect following, cookies and credentials; no response bodies are read. Concurrency is 16, each request has a one-second timeout, headers are limited to 16 KiB, and the overall probe deadline is ten seconds. Deadline truncation is explicitly displayed. The OS listener enumeration precedes this deadline.
- Page entry and service mutations refresh detection; manual Refresh is available. Leaving cancels active requests. A scan-generation reference prevents an obsolete completion from replacing newer state. Other services are never stopped, reconfigured, or given firewall rules by discovery.
- Managed-instance labeling requires both the current process ID and active service port. Other process metadata is a best-effort snapshot and may become stale. A local response is not evidence of public-internet reachability.
- No new package dependencies. Both languages use matching resources/placeholders. Existing WinUI themes, wrapped actions, scrolling and navigation behavior apply to new rows.

Validation includes 92 .NET tests, with real IPv4/IPv6 listener enumeration, Windows PID checks, varied HTTP statuses, silent/non-HTTP sockets, cancellation, duplicate suppression, unavailable processes, and proof that redirects/bodies are not consumed. The Windows packaged GUI harness checks individual clipboard URLs, discovery before managed startup, an independent HTTP fixture, automatic/manual refresh, restart/stop stale-address removal, and the existing lifecycle. Windows CI additionally runs firewall integration, the 168-combination page/theme/language/size matrix, dependency audits, native helper tests and all three architecture builds/installers.

Limits: only plain HTTP using an IP Host header is detected. HTTPS-only, hostname-only and slow services may be absent. HEAD probes can appear in target access logs. Browser/Explorer launch, physical x86/ARM64 execution and public routing remain environment-specific manual checks. This review is not a penetration test.
